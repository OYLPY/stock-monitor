# PMO 文档治理标准

> Doc ID: DOC-0028 · 完整 lifecycle、authority 与 tags 以 [文档目录](DOCUMENT_INDEX.md) 为准。

## 目的与边界

本标准治理文档如何命名、编号、定位、关联、修订和退役。它是 **PMO 过程标准**，不决定产品行为，也不替代 PRD、需求、ADR 或系统设计的专业事实。

## 文档层级与权威性

文档治理和产品内容采用两条权威轴，避免把 PMO 误解成产品设计来源：

| 范围           | 顺序                                                                                  | 作用                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 执行约束       | 明确用户/平台安全约束 → `AGENTS.md` → PMO 文档治理 → 主题文档内的局部编辑约定         | PMO 统一文档编号、命名、目录、tags、模板、生命周期和变更流程；这些规则高于系统设计文档中的局部文档组织约定，但不决定产品行为。 |
| 产品与技术内容 | 产品范围/需求 → 已接受 ADR 与系统架构 → 领域设计/接口契约 → 运维手册 → 实现与测试证据 | 上层定义目标和约束，下层说明实现方式或已观察到的事实；计划和研究资料提供路线或证据，不替代产品需求或已接受决策。               |

内容冲突按上表第二行处理，并同时服从执行约束。代码与测试日志是当前实现行为的事实，不自动成为规范意图；若它们与权威需求或设计不符，应通过 Issue 修正文档或实现并保留验证证据。同一主题指定一个权威文档，其余文档链接到它。

目录中的 `Authority` 使用受控值：

| Authority                 | 解释                                             |
| ------------------------- | ------------------------------------------------ |
| `process-policy`          | 文档治理流程规则；只在自身治理范围内具有约束力。 |
| `product-requirement`     | 产品目标、功能/非功能需求和用户场景。            |
| `architecture-decision`   | 已接受或待议的架构决策及后果。                   |
| `architecture`            | 当前系统边界、模块和运行拓扑。                   |
| `design-contract`         | 领域行为、API、数据、风险和安全设计约束。        |
| `operational-guidance`    | 经验证的操作、故障处理和恢复步骤。               |
| `implementation-evidence` | 代码或测试记录的当前实现事实，不定义规范意图。   |
| `planning-reference`      | 阶段路线、里程碑和依赖计划。                     |
| `task-index`              | GitHub Issue 与任务状态入口。                    |
| `requirement-index`       | 需求编号、分类和需求间导航。                     |
| `traceability-index`      | 需求到设计、实现和验证的关系映射。               |
| `navigation`              | 文档入口和检索指引。                             |
| `document-metadata`       | Doc ID、tags、生命周期和文档关系目录。           |
| `research-evidence`       | 有来源和时点标记的外部调查结论。                 |
| `external-reference`      | 第三方或外部规则的引用记录。                     |
| `process-reference`       | 模板或工程过程说明；本身不定义产品行为。         |

新 Authority 必须能改变内容裁定方式；仅表示主题或文件格式时使用 `Type` 或 tags。

## Doc ID 与旧编号

- 每份长期维护的文档在目录获得全局单调递增 ID：`DOC-0001`、`DOC-0002`……，固定四位数字；不编码阶段、目录、类型或状态。
- 新 ID 取目录当前最大值加一。目录中的 ID 是身份；改标题、路径、阶段、tag 或文档类型都不改变 ID，也不重新编号。废弃 ID 永不复用。
- 现有 `ADR-0001`、RQ/FR/AC、P00–P13 和 Issue 号继续承担原职责；目录 `Aliases / refs` 收录需要检索的旧编号，它们不等于 Doc ID。
- 新建文档时先分配 ID，再从模板建立文件；文档首部标 `Doc ID` 并链接回目录。旧文档不批量加头部或重命名；首次实质修改时按任务范围补充 Doc ID。
- 文件名使用小写 kebab-case 和主题，例如 `backtest-engine.md`；不把阶段号、Doc ID、状态或日期写进稳定文件名。现有文件名保持原样。

## 文档类型

`Type` 从目录中受控的类型集合选择；目录行不得临时造类型。当前类型及用途如下：

| Type           | 用途                                             |
| -------------- | ------------------------------------------------ |
| `adr`          | 记录一项已接受或待议决策及其后果。               |
| `architecture` | 定义系统边界、模块和运行拓扑。                   |
| `contract`     | 定义 API、数据来源或持久化 schema 的可核验契约。 |
| `design`       | 定义领域设计、策略、风险、失败或安全行为。       |
| `evidence`     | 记录已执行测试、运行和验收的事实。               |
| `guide`        | 说明工程过程或可恢复上下文工作方式。             |
| `index`        | 导航文档、任务或需求集合。                       |
| `notice`       | 记录第三方、许可或法律声明。                     |
| `plan`         | 说明阶段、依赖和交付路线。                       |
| `product-spec` | 定义产品目标、范围和主要用户行为。               |
| `requirements` | 细化功能或非功能要求。                           |
| `research`     | 记录外部资料调查、方法和证据边界。               |
| `standard`     | 规定跨文档或跨主题必须遵循的规则。               |
| `taxonomy`     | 维护受控分类词汇。                               |
| `template`     | 提供可复制的文档结构。                           |
| `traceability` | 映射需求、设计、实现和验证入口。                 |
| `use-cases`    | 描述用户场景、触发条件和可验收结果。             |

若确有新类型需求，先在 Issue 中说明它改变的模板或权威行为，再同步本标准和目录；能够归入现有类型时不扩充集合。

## 生命周期与修订

目录使用以下 lifecycle：

| Lifecycle    | 含义                                                             |
| ------------ | ---------------------------------------------------------------- |
| `draft`      | 已注册，内容仍待完成；不可作为最终规范。                         |
| `active`     | 当前适用的权威版本。                                             |
| `superseded` | 被新 Doc ID 替代；保留路径、替代链接和历史，不作为默认检索结果。 |
| `archived`   | 不再适用且没有直接替代；保留原因和最后可用上下文。               |

每项文档 metadata 由 [DOCUMENT_INDEX.md](DOCUMENT_INDEX.md) 唯一维护：Doc ID、标题、类型、lifecycle、authority、tags、keywords、路径、旧编号/关联文档。正文只重复 Doc ID 作为可见身份；生命周期、authority 和 tags 不在正文再维护一份。

- 文档语义不变的排版/错字修正只更新目录路径或 `Updated` 日期（若目录中维护）；规范语义变化通过对应 Issue 记录，并修正受影响文档、关联链接和需求追踪。
- 新决策应新增 ADR；新版本设计通常保留同一 Doc ID 并增加文档内修订记录，除非其职责/权威主题改变。完全替代或拆分主题时，为新文档分配新 ID，并将旧条目标为 `superseded`、指向替代项。
- 重命名/移动文件只有在路径本身有问题时进行；同一 Issue 中更新目录、所有 Markdown 链接和 Agent 入口，并验证无断链。
- 删除只允许移除重复的纯编辑草稿或临时产物；有决策、需求、证据或被其他文档引用的文件应 supersede/archive，不硬删历史。

## Tags 与文档类型

`type`、`lifecycle`、`authority`、`phase` 和 `tags` 是不同字段。tag 只表示可复用主题，采用 [受控词表](TAG_TAXONOMY.md)，不把类型、状态或任务结果再编码成 tag。

- 每份文档使用 2–6 个已有 tag；至少一个 `domain/*`，适用时带 `phase/*` 或 `market/*`。
- 只在一个概念会帮助跨文档检索时新增 tag；单篇特有词放入 `Keywords`。新增/改名 tag 必须同步词表和所有受影响目录行。
- `type` 选择最具体的已有类型；新类型需能区分模板或权威行为，不能为某一份文档临时发明。

## 索引与检索

- [docs/INDEX.md](../INDEX.md) 是首屏导航；它只链接到权威目录、任务索引、需求索引和主计划，不复制长清单。
- [DOCUMENT_INDEX.md](DOCUMENT_INDEX.md) 是所有长期文档 metadata 的唯一目录；一行对应一个 Doc ID，表头和字段固定、单元格不跨行。
- `docs/ISSUE_INDEX.md` 管任务与阶段，`REQUIREMENTS_INDEX.md`/`TRACEABILITY.md` 管需求关系，文档目录管文档身份/定位。三种索引互链但不合并。
- 目录支持精确 ID、旧编号、tag、类型、路径和关键词查找；全文内容用 `rg` 搜索。检索器默认排除 `superseded` 和 `archived`，除非需要历史决策。
- 未来 RAG 按标题层级切块；每块携带 `doc_id`、`title`、`type`、`lifecycle`、`authority`、`tags`、`phase`、`path` 和 section heading，引用回原文件/标题。先按生命周期/authority 做过滤，再用词法或向量检索；不丢掉来源链接。

## 文档变更工作流

1. **定位**：读 [docs/INDEX.md](../INDEX.md)、当前 Issue 和文档目录；确认权威文档、直接依赖及相关 RQ/FR/AC/ADR。
2. **定范围**：在 Issue 记录文档 ID、预期变更、影响文档、验收和验证；不要仅为规范格式批量改写无关文件。
3. **新增**：取下一个 Doc ID，选现有 type/tag/模板，创建描述性路径，正文标识 Doc ID，目录新增完整行并链接来源/相关文档。
4. **修改**：在同一 Issue 更新权威正文和目录条目；同步真正受影响的需求追踪、设计引用、阶段索引和模板/词表。若改行为/策略，先检查 ADR 和下游实现/测试责任。
5. **替代/迁移**：先创建或确定 successor，再同步更新引用和 `Related / supersedes`，验证旧链接与新链接，最后把旧条目设为 `superseded` 或 `archived`。
6. **验收**：核对 Doc ID 唯一、路径存在、tag 已注册、链接有效、层级引用无冲突；运行适用的格式、类型、lint、测试、构建和 CI。设计文档不声称尚未实现的运行时行为已验证。
7. **交付**：按本仓库当前授权直接提交/push `main`，确认 Quality CI，再更新 Issue 证据并关闭；不创建 PR。提交内容应包含文档、索引/tag/追踪更新及本任务交接。

## 完成标准

文档任务只有在内容可追溯、目录/tag 与链接一致、证据级别明确、Issue 验收日志完整且推送提交的 CI 成功后才算完成。目录不是全文摘要；每个主题的权威定义仍只保存在其权威文档中。
