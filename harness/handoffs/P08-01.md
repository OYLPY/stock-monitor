## Established facts

- `main` started at `dc0731789fe82dd841942f5e38fe61e671e9d684`; the worktree was clean and no PR was open. Dependencies #33 and #39 were closed.
- `@openai/codex-sdk` and its bundled CLI are pinned to `0.169.0`. The bare default provider made 37 loopback requests on connection loss. The SDK exposes no request counter or awaited child-process exit handle.
- The built-in provider rejects provider-specific retry overrides. The adapter now selects a session-local `stock_monitor_openai` provider with `requires_openai_auth=true`, `request_max_retries=0`, `stream_max_retries=0`, and `supports_websockets=false`; it does not write the user's `CODEX_HOME/config.toml`.

- Two scratch directories from an earlier cleanup reproduction may remain under the Windows temp directory after `Remove-Item -Recurse` was blocked by policy. Later bounded `rm` retry runs cleaned up their own temporary directories; no matching Codex PoC process was running.

## Dead ends

- Disabling only `features.unbounded_connection_retries` did not bound retries; the bare SDK reached 37 requests. Aborting on the first emitted SDK error reduced a connection-drop case to 3, but did not guarantee the hard request budget.
- Setting retry fields under reserved built-in provider ID `openai` fails configuration before sending a request. Defining a non-reserved auth-required provider with zero request/stream retries and WebSocket disabled passed the same loopback cases at one request each.
- The local 429 fixture is classified by the updated provider path as `RATE_LIMITED`; this does not prove account quota semantics.
- The first PoC cleanup raced SDK child shutdown. Bounded cleanup retries worked on later runs; do not infer that an aborted remote request was terminated.
